# Formal Proposal Amendment: Flask-Based DairyIQ Prototype

## Project Title

**Application of a Random Forest Model for Milk Quality Classification and
Development of a Flask-Based DairyIQ Prototype System for Ugandan Dairy
Processing Plants**

## Purpose of This Amendment

This amendment formally replaces the proposed PyQt5 desktop architecture with
the Flask-based DairyIQ web application implemented in the project repository.
The research problem, machine-learning objective, target users, and intended
decision-support purpose remain unchanged.

The architectural change is justified by the need for:

- centralized model and application maintenance;
- access from computers, tablets, and smartphones through a web browser;
- authenticated access for authorized dairy personnel;
- centralized storage of milk-batch records;
- historical analysis across collection centers and districts;
- report generation and export;
- easier future integration with sensors, mobile clients, and APIs.

This amendment does not authorize unsupported research claims. Dataset size,
model performance, comparison-model results, and usability findings must be
reported from reproducible evidence generated by the completed study.

## Authoritative System Description

DairyIQ is a responsive Flask-based decision-support web application that uses
a trained Random Forest classifier to classify raw milk quality into:

- `Low`
- `Medium`
- `High`

Authorized users enter milk collection details and laboratory measurements
through a browser-based form. The Flask backend validates the submitted values,
constructs the model input using the approved feature order, obtains a
classification from the Random Forest model, generates standards-based
observations, and stores the batch record in Firebase Firestore.

The system provides:

- authenticated user access;
- milk-batch and transport-information capture;
- manual entry of milk-testing measurements;
- Random Forest milk-quality classification;
- result visualization and standards-based observations;
- historical batch records;
- district and collection-center analytics;
- report and table export;
- centralized storage through Firestore.

## Approved Target Feature Contract

Subject to final validation against the approved dataset and milk-quality
standard, the transformed Flask prototype and Random Forest model will use
these 11 laboratory, sensory, and appearance features:

1. pH;
2. temperature;
3. taste;
4. odor;
5. fat content;
6. titratable acidity;
7. protein content;
8. lactose content;
9. Total Plate Count (TPC);
10. Somatic Cell Count (SCC);
11. color.

The three sensory and appearance parameters are required prediction inputs and must be included
in the authoritative dataset, preprocessing pipeline, web form, Flask
validation, model artifact, Firestore records, reports, and automated tests.
The existing nine-feature model artifact cannot make valid 11-feature
predictions and must be retrained or replaced before these fields become
active in production.

`SNF` is not part of the approved model input contract. It may be retained only
as non-model metadata if needed by the operational record. `Turbidity` must not
be added because it is not part of the approved thesis feature contract.

The initial encoding contract is:

| Feature   | Encoded value `1`              | Encoded value `0`              |
|-----------|--------------------------------|------------------ -------------|
| Taste     | Normal or acceptable taste     | Abnormal or off-taste          |
| Odor      | Fresh or normal odor           | Abnormal or objectionable odor |
| Color     | Normal creamy-white appearance | Abnormal appearance            |

The exact assessment procedure and user-facing wording must be approved by a
milk-quality domain expert.

The taste parameter must follow a documented safe assessment protocol. The
system must not direct operators to consume potentially contaminated raw milk.
If safe tasting is not approved, `Taste` must represent a documented historical
or laboratory-derived assessment rather than an instruction to taste a sample.

## Revised General Objective

To develop and evaluate a Random Forest model for milk quality classification
and integrate it into a Flask-based DairyIQ web application to support milk
quality assessment and decision-making in Ugandan dairy processing plants.

1. To identify and preprocess the laboratory, sensory, and appearance
   measurements required to classify raw milk into defined quality categories.
2. To develop and evaluate a Random Forest model for milk quality

3. To design and implement a responsive Flask-based web application that
   applies the trained Random Forest model and supports authenticated batch

4. To assess the usability and practical applicability of the Flask prototype

3. How can the Random Forest model be integrated into a responsive Flask web

## Revised Content Scope

The study covers milk-quality classification using the approved 11-feature
contract combining laboratory measurements with taste, odor, and color
assessments. It includes dataset validation, preprocessing, Random
Forest development, comparative model evaluation where academically required,
model validation, and integration into a Flask-based prototype.

The prototype covers authentication, manual laboratory, sensory, and appearance

The study does not include direct sensor automation, real-time streaming,

## Revised System Architecture

The DairyIQ system uses a client-server web architecture with the following
components:

### Presentation Layer

HTML, CSS, JavaScript, Jinja templates, Chart.js, and DataTables provide the
browser-based interface, validation feedback, charts, tables, and exports.

### Application Layer

Flask manages routes, sessions, form processing, input validation, model
inference, standards-based observations, history retrieval, and result
rendering.

### Machine-Learning Layer

The approved Random Forest artifact is loaded using joblib. Input data is
constructed using the exact feature names and order used during training. The
model returns one supported quality class and, after validation or calibration,
may provide class probabilities and confidence information.

### Data and Authentication Layer

Firebase Authentication verifies authorized users. Firebase Firestore stores
batch metadata, laboratory values, prediction results, model metadata,
observations, and timestamps.

### Deployment Layer

Gunicorn serves the Flask application in the deployment environment. Users
access the prototype through a supported web browser on a computer, tablet, or
smartphone connected to the hosting environment.

## Revised Methodology: Prototype Design

The prototype will be developed using an iterative software-engineering
approach. Requirements will be derived from the research objectives, intended
operator workflow, approved feature contract, and milk-quality standards.

The interface will organize the workflow into:

1. user authentication;
2. batch and collection information entry;
3. laboratory, sensory, and appearance measurement entry;
4. input validation;
5. Random Forest prediction;
6. result and observation presentation;
7. persistent batch storage;
8. historical analysis and export.

Responsive design will be used so that the application remains usable across
common desktop and mobile screen sizes. Form controls will restrict invalid
entries where practical, while the Flask backend will remain the authoritative
validation layer.

## Revised Methodology: Model Integration

The selected and validated Random Forest model will be serialized with joblib
and loaded by the Flask application during startup. The application will verify
that the artifact uses the approved features and classes.

For each prediction:

1. Flask receives the submitted form values.
2. Server-side validation checks completeness, numeric format, finite values,
   approved physical ranges, and valid sensory encodings.
3. The values are assembled into a pandas DataFrame using the model's exact
   feature order.
4. The Random Forest model generates a quality classification.
5. Class probabilities are generated using `predict_proba()` when supported.
6. Standards-based observations are calculated separately from the ML result.
7. The batch, measurements, prediction, model version, and timestamp are stored
   in Firestore.
8. The browser displays the result, measurements, observations, and charts.

The preprocessing pipeline must encode taste, odor, and color using
the same mapping during training and inference. User-facing labels must be
stored alongside encoded values so that each prediction remains auditable.

## Revised Methodology: Expanded Dataset

The authoritative dataset must contain all 11 target features for every sample.
The four added parameters must contain meaningful, domain-valid variation and
must not be introduced as constant or arbitrarily populated columns.

For taste, odor, and color, the study must
document:

- the assessment definitions;
- who performed or generated the assessment;
- the collection or synthesis procedure;
- the encoding map;
- handling of uncertain or missing observations;
- inter-rater agreement where multiple assessors are used;
- class distributions and feature distributions.

The study will compare the existing nine-feature candidate with the expanded
11-feature candidate using identical evaluation splits. This comparison will
show whether the added parameters improve generalization, macro F1, and recall
for `Low` and `Medium` quality classes.

## Revised Methodology: System Testing

The Flask prototype will be evaluated through:

- unit testing of input parsing and validation;
- model-contract testing;
- sensory-encoding and validation testing;
- prediction regression testing;
- Flask route and authentication testing using test doubles;
- Firestore success and failure testing;
- integration testing of the complete prediction workflow;
- responsive-interface testing;
- browser compatibility testing;
- report and table-export testing;
- usability testing with representative intended users.

Usability evidence should include participant criteria, tasks, task-completion
rates, observed errors, completion time, a recognized usability questionnaire
where approved, qualitative feedback, and resulting interface changes.

## Revised Functional Requirements

The system shall:

1. authenticate authorized users;
2. allow users to log out and protect restricted routes;
3. capture collection-center, district, transport, tester, and volume details;
4. capture all approved milk-quality measurements;
5. capture taste, odor, and color using controlled input fields;
6. validate laboratory and sensory input before prediction;
7. classify milk as `Low`, `Medium`, or `High`;
8. present standards-based observations separately from the ML result;
9. save all 11 inputs, the batch, and the prediction to Firestore;
10. display the result and entered measurements;
11. display historical batch records and quality trends;
12. provide district and collection-center analytics;
13. export supported reports and historical tables;
14. identify the model version used for each new prediction.

## Revised Non-Functional Requirements

The system should provide:

- usability through clear forms, labels, feedback, and color-coded results;
- responsiveness across supported screen sizes;
- security through authentication, protected routes, secret management, and
  server-side validation;
- reliability through controlled model loading and Firestore error handling;
- maintainability through separated model, application, and configuration
  concerns;
- traceability through model version and prediction timestamps;
- acceptable prediction response time on the approved hosting environment;
- compatibility with current supported web browsers.

## Connectivity Limitation

The Flask and Firebase architecture is not fully offline. It requires access to
the deployed application and Firebase services. The dissertation must therefore
remove claims that the implemented prototype operates without internet access.

Where intermittent connectivity is a concern, the study should state this as a
limitation and recommend one or more future improvements:

- deployment on a local plant network;
- queued local storage with later synchronization;
- a progressive web application;
- a separate offline desktop client using the same validated model artifact.

## Revised Expected Output

The expected output is a functional Flask-based DairyIQ prototype through which
authorized users can enter milk-batch information and all 11 laboratory,
sensory, and appearance parameters, obtain a Random Forest quality
classification, review supporting observations and visualizations, store the
result, inspect historical records, and export reports.

The prototype is a decision-support tool. It does not independently certify
regulatory compliance or replace confirmatory laboratory procedures unless such
use is separately validated and approved.
